> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship 0.2.6, the release of #26, #27, #28 and #29. The version labels say 0.2.6, the changelog section is dated and each bullet matches the merged code, a hands-on upgrade from 0.2.5 has been run in a throwaway home before the tag, the tag is pushed and the owner approves the publish, and the machine's own installs are upgraded and verified afterwards.

**Tech Stack:** `VERSION`, `package.json`, `CHANGELOG.md`, `tools/release_check.py`; `npm pack`, Node 24 and Python 3.10-3.13 for the hands-on run; `gh` and `git` for the tag.

Branch: `chore/0.2.6-release`, cut from `origin/main` at 0d6ca6d or later. The plan is the branch's first commit. ## Global Constraints

- The release procedure is `.github/skills/shipping-a-change/SKILL.md`. Where this plan and the skill differ, the skill wins, with one exception: the controller pushes the tag under the owner's standing permission ("You are good to handle the publishing tag"), which narrows the skill's step 4 ("The owner pushes the tag"). A later task can correct that skill in its own commit; this plan does not edit it. Where the skill is silent, this plan says so and does not invent the npm or GitHub flow.
- A person reads the diff of `VERSION`, the `version` in `package.json` and `.github/workflows/release.yml` before merge (AGENTS.md, "Never merges without a human"). "Merge it when done" does not count. The agent never merges; the owner merges.
- A publish cannot be undone and npm refuses to reuse a version. A failed release is fixed by re-running the workflow, never by a new tag for the same version (skill).
- `VERSION` and `package.json` `version` change together. The file is `skills/deeper-reading/VERSION` (plan B moved it); `release.yml` and `tools/release_check.py` read it there.
- `tests/fixtures/installed-files-0.2.5.json` is a record of 0.2.5 and is never edited.
- Hands-on runs use a throwaway `HOME` and `USERPROFILE` and never the real home, except D4, which is the one step that does and is an owner-visible step. No disk-wide searches; scratch folders are named by the controller and deleted at the end.
- Commit subjects are conventional; no attribution lines unless the repository's rules say so; merge commits only; never `--amend`, rebase, reset or `--no-verify`. The controller pushes the tag (standing permission); nothing else is pushed by an agent.
- A claim in the changelog, a commit or a report states only what the diff or the run shows.

- Changelog heading: `## 0.2.6 - YYYY-MM-DD` (hyphen, real calendar date, the date D1 lands). The `## Unreleased` heading is replaced, not duplicated; a fresh empty `## Unreleased` above it is not added unless `tools/release_check.py` needs it (it does not).

- Issues outside milestone 0.2.6 (R64); they belong to 0.2.7.
- Changing `release.yml`, the Release workflow, or the npm trusted-publisher setup. The `npm-release` environment and the tag rule are the owner's, and are a precondition (skill), not a task.

## Risks and open questions

- **Stack merged.** Paths in this plan were checked against 0d6ca6d.
- **Gate block.** The gate block matches the workspace `constraints.md` (checked at 0d6ca6d). If it ever differs, the packet is rebuilt with `packet.py build --reconcile` and this block follows `constraints.md` (R100).
- **Hosted CI on the release branch.** The `release-labels`, `lint`, `test` and `node` jobs run on the pull request as for any other PR. Whether the skills-ref validation plan C adds to CI needs anything on the release branch is not determined from the sources.
- **Two approvals, one hour.** The `release` job waits up to 60 minutes for the version to be public (skill step 8). The owner approves the environment first (no time limit stated by the skill); the hour starts when the `release` job starts, after the version is staged, and the staged version must be approved within it; the skill says what to re-run if the wait times out. Approval waits for npm's malware scan; its duration is not stated by the skill.
- **Not determined from the sources.** The skill does not say how the owner is told a stage is waiting, nor whether the `npm stage` commands need a particular npm version on the machine. This plan does not guess; D3 follows the skill and the owner's own UI.
- **Date of the heading.** `release_check.py --tag` accepts any real date. The heading takes the day D1 lands; if the merge slips by days, whether to re-date is the owner's call. The tool does not check that the date is the release day.
- **Refusal for an edited file (D2 Step 3).** Known from `installer/core.py`: message `modified managed files: <paths>`, no code, no recovery text; the recovery is `uninstall --force` then `install` (USAGE, CHANGELOG). If plan A or B changed this, D2 Step 3 follows the merged code.
- **D2 touches the network and a real Codex binary.** `npm pack deeper-reading@0.2.5` needs the registry; check 2 needs a Codex version close to 0.164.0-alpha.11.1, the one the 0.2.6 claim of 7 to 1 skills was measured on. A different Codex may list differently; the report names the version used.
- **Probes read the real home.** `probes/codex_list.py` reads the real `~/.agents` read-only; its output must be filtered on its own cwd. All other commands use the throwaway home. A command that ignores `HOME` (a tool that reads the real profile through another variable) is not ruled out by the sources; the report states what each tool resolved.
- **D4 changes the real home.** If an existing install there has no receipt or is owned by another target (a state the 0.2.6 guard now refuses), D4 stops at the refusal and asks the owner; recovery deletes files.
- **Failure after the tag.** A failed publish is fixed by re-running the workflow, never by a new tag for the same version (skill). If D2 missed a defect that is found after publish, the fix is a 0.2.7 release; 0.2.6 cannot be replaced.
